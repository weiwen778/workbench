# 宠物模块（像素狗）设计

日期：2026-11-14
状态：已确认（2026-11-14；默认形象见「像素素材规范」）

## 背景

用户想在工作台里加一个独立的虚拟宠物模块，原话是「模仿真实的宠物那样，会在某些时候有饥饿」。经过讨论，确定：

- 虚拟宠物，不是现实宠物的管理档案。
- 像素风，养狗，可以改名。
- 「中间方案」：有真实的衰减和生病，但节奏很慢，不惩罚短期忙碌，没有永久死亡。

工作台目前是单用户、自托管的 React + MUI 前端 + FastAPI + SQLAlchemy 后端，已有打卡、待办、表格、笔记等模块。宠物模块独立成页，只从打卡/待办读取「今天有没有完成事项」用于每日奖励，不修改这些模块的界面和流程。

## 目标

- 一个独立的 `/pet` 页面：领养、喂食、洗澡、玩耍、遛狗、睡觉、抚摸、看医生、喂零食。
- 饥饿、清洁、心情、精力按真实时间衰减；关掉网页也在变，下次打开按时间戳补算。
- 连续约 3 天不管会明显变饿、变脏；约 4 天左右生病；没有永久死亡。
- 持续照顾 7 天进入成年期，30 天进入老年期。
- 每天第一次打开时，如果当天完成过打卡或待办，狗狗获得心情和一份零食（单向、轻量）。
- 状态和操作全部落库，换浏览器、备份恢复后保持一致。

## 非目标

- 不做永久死亡、离家出走、丢失宠物。
- 不做多宠物同时养、品种繁育、配对。
- 不做货币、商店、排行榜、社交、交易。
- 不做后台推送、邮件、桌面通知。
- 不做 AI 对话、语音。
- 不做全局悬浮桌宠（后续可以用 oneko.js 的方式单独加）。
- 不把宠物状态塞进打卡页、待办页，不反向提醒或惩罚用户。
- 不做宠物状态的历史曲线和图表。

## 反目标

即使功能「能用」，以下情况也算失败：

- 用户度假三天回来发现宠物死了或永久受损。
- 宠物变成每天必须点十几次的负担。
- 为了维持状态需要理解一套复杂的数值系统。
- 宠物动画或轮询拖慢工作台其他页面。

## 约束

- 后端时间统一用 `models.utcnow()`（naive UTC）；跨天判断用 `utils.now_local()` / `today_local()`。
- 不新增后台调度器。状态在读取和操作时按时间戳补算。
- 模型带 `user_id`，与现有表一致，尽管当前是单用户。
- 前端请求走 `@/api/client` 的 `http`，自动带 CSRF。
- 素材必须可商用、许可清楚，记录到 `CREDITS.md`。
- 新增表自动进入现有整库备份（`pg_dump` / SQLite 文件），无需改备份服务。
- 不引入新的前端依赖；动画用 CSS + Framer Motion（已有）。

## 方案

### A. 后端权威 + 时间戳补算（已选）

状态存一行，后端读取时按 `now - last_tick_at` 逐小时补算并写回；动作走接口，后端校验冷却和收益。

- 多端一致，备份/恢复天然覆盖。
- 不依赖浏览器时钟，不跑常驻定时器。
- 代价是多一张表和一组接口。

### B. 前端模拟 + 后端只存快照

动作在前端立即结算，定期同步。

- 交互零延迟，但多设备会覆盖、清缓存会丢，且与工作台「显式保存才落库」的边界冲突。放弃。

### C. 后端定时任务真推进

调度器每分钟 tick。

- 最像真实宠物，但单用户自托管场景过度设计，容器重启、时区、重复执行都要处理。放弃。

结论：选 A。用「读取时补算」获得 C 的真实感，避开 B 的一致性问题和 C 的运维成本。

## 设计

### 模块边界

- 前端：新增 `/pet` 页面，不改打卡、待办、表格等模块的界面。
- 后端：新增 `pets` 表、`/api/v1/pet` 路由、`services/pet.py` 规则引擎。
- 唯一的跨模块读取：每日奖励时查询「今天是否有完成的打卡项或待办」。只读，不写回。
- 导航：在 `app-nav.ts` 新增「生活」分组，放入「宠物」。不默认固定到侧栏，用户可在「全部导航」里自行固定。

### 数据模型

新增 `Pet`（表 `pets`），一个用户最多一行：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int PK | |
| user_id | FK users.id, unique | 级联删除 |
| name | String(40) | 默认「旺财」，1–12 字 |
| species | String(16) | v1 固定 `dog` |
| satiety / cleanliness / mood / energy / health | Float | 0–100，保留小数；payload 四舍五入成整数 |
| sleeping | bool | 是否在睡觉 |
| sick_since | datetime? | 生病起始时间；为空表示健康 |
| sleep_started_at | datetime? | |
| care_days | int | 被照顾过的天数 |
| last_care_date | date? | 本地日期 |
| last_tick_at | datetime | 上次结算时间，非空 |
| last_fed_at / last_washed_at / last_played_at / last_walked_at / last_vet_at / last_treated_at / last_petted_at | datetime? | 冷却 |
| poop_count | int | 0–3 |
| poop_progress | float | 清醒累计小时，满 8 小时生成一堆 |
| neglect_since | datetime? | 有核心状态低于 10 的起始时间 |
| pet_bonus_hour | datetime? | 抚摸奖励的整点桶 |
| pet_bonus_total | int | 当前小时已获得的抚摸心情 |
| treats | int | 0–5 |
| daily_bonus_date | date? | 每日奖励领取日期 |
| version | int | 预留并发控制 |
| created_at / updated_at | datetime | 现有 `TimestampMixin` |

索引：`user_id` 唯一索引。`user_id` 上的唯一约束同时承担查询索引。

初始值（领养时）：饱腹 70、清洁 90、心情 80、精力 80、健康 100、零食 0、`last_tick_at = now`。

### 时间推进算法

`advance(pet, now)`：

1. 计算 `elapsed = now - last_tick_at`，最多补算 90 天（超过按 90 天处理，宠物不会死亡，只是生病）。
2. 以「最多 1 小时」为步长循环，最后一步可以是小数小时。
3. 睡觉时：
   - 精力 `+12/小时`；
   - 其他三条状态按 50% 速度衰减；
   - 不累计便便时间；
   - 精力到达 100 时自动醒来，剩余步长按清醒处理（在当前步内切分）。
4. 清醒时按下面的衰减表计算；便便堆会放大清洁和心情的衰减。
5. 更新 `neglect_since`：
   - 当 `min(饱腹, 清洁, 心情, 精力) < 10` 且 `neglect_since` 为空时，记为当前时间；
   - 当最小值回到 10 以上时清空；
   - `neglect_since` 已存在超过 12 小时，健康 `-20/天`。
6. 健康恢复：没有处于忽视状态且四项核心状态都 ≥ 40 时，健康 `+8/天`。
7. 健康下限 10，不会到 0。
8. 便便：每累计 8 个清醒小时生成 1 堆，最多 3 堆；到 3 堆后进度停在 8 小时，不再累计。洗澡清空堆数并把进度归零。
9. 生病状态：健康第一次 ≤ 60 时写入 `sick_since`；健康 ≥ 75 时清空。生病期间心情衰减 ×1.5、精力衰减 ×1.25，禁用玩耍和遛狗。用持久化字段而不是实时比较健康值，避免 61–74 区间反复横跳。
10. 写回 `last_tick_at = now`。

逐小时循环最多 2160 次，单次 <1ms，便于测试和推理。

### 数值表

衰减（每清醒小时）：

| 状态 | 衰减 | 备注 |
| --- | --- | --- |
| 饱腹 | -1.5 | 满值约 66 小时见底 |
| 清洁 | -0.8 | 乘以便便系数 |
| 心情 | -1.2 | 乘以便便系数和生病系数 |
| 精力 | -1.5 | 乘以生病系数 |
| 健康 | 见上 | 忽视 -20/天；恢复 +8/天 |

便便系数：清洁 `×(1 + 0.5 × 堆数)`，心情 `×(1 + 0.25 × 堆数)`。

生病：健康第一次 ≤ 60 时记录 `sick_since`，健康 ≥ 75 时清除（滞回，避免反复横跳）。生病期间心情衰减 ×1.5、精力衰减 ×1.25，禁用玩耍和遛狗；状态标签和前端动画都以 `sick_since` 为准，不看当前健康值。边界情况：健康 61–74 且 `sick_since` 为空时视为「刚好转」，可以正常玩耍。

动作：

| 动作 | 效果 | 冷却 | 限制 |
| --- | --- | --- | --- |
| 喂食 | 饱腹 +40 | 30 分钟 | 饱腹 ≥ 95 时提示已吃饱 |
| 零食 | 饱腹 +15、心情 +8，消耗 1 份 | 60 分钟 | 没有零食时禁用 |
| 洗澡 | 清洁 +50、清空便便、精力 -5 | 2 小时 | 睡觉时不可用 |
| 玩耍 | 心情 +20、精力 -8 | 20 分钟 | 精力 ≥ 20；生病时不可用 |
| 遛狗 | 心情 +25、饱腹 -6、精力 -12 | 4 小时 | 本地时间 07:00–22:00；精力 ≥ 25；生病时不可用 |
| 睡觉 / 叫醒 | 切换睡眠 | 无 | 叫醒随时可用 |
| 看医生 | 健康 +20 | 8 小时 | 健康 < 85；睡觉时不可用 |
| 抚摸 | 心情 +3 | 5 秒 | 每小时最多 +15；**不计入照顾**；达到小时上限后冷却显示到下一个整点 |

- 所有动作在结算前先执行一次 `advance`，保证冷却是基于最新状态。
- 睡觉时只有「叫醒」可用。
- 「照顾」动作 = 喂食、零食、洗澡、玩耍、遛狗、看医生；抚摸和睡觉不算。

### 成长

- 一个本地日期里至少完成 1 次「照顾」动作，`care_days +1`（每天最多一次）。
- 幼犬：0–6 天；成年：7–29 天；老年：30 天起。
- 阶段只影响文案、显示缩放和轻微色调，不改变衰减速度（v1 保持简单）。
- v1 只用一套精灵图：幼犬按 0.85 倍显示，成年 1.0 倍，老年 1.0 倍并加低饱和滤镜。三套阶段素材留到后续，避免第一版被美术量拖住。

### 状态标签

按优先级取第一个命中的：

1. 睡觉中
2. 生病了（`sick_since` 不为空）
3. 饿坏了（饱腹 ≤ 20）
4. 困得不行（精力 ≤ 20）
5. 脏兮兮（清洁 ≤ 20）
6. 不开心（心情 ≤ 20）
7. 精神很好（四项都 ≥ 70）
8. 还不错

前端同时拿到每个状态的数值，标签只用于营造氛围，不作为唯一信息。

### 每日联动奖励

- 每天第一次 `GET /pet` 时检查：`daily_bonus_date != 今天`，且今天有已完成的打卡项或待办。
- 满足则：心情 +6、零食 +1（上限 5）、`daily_bonus_date = 今天`，响应里带 `daily_bonus` 供前端弹一句提示。
- 同一天只发一次；不看连续天数，不做惩罚。
- 没有完成事项就没有奖励，不显示红色提醒。
- 查询只读 `checkin_instances.completed_at` 和 `todos.completed_at`，按本地零点换算成 UTC 后比较，各取一条即可。
- `checkin_instances` 和 `todos` 目前没有 `user_id`，两表是全局数据；v1 的奖励查询也是全局的，在单用户部署下等价于当前用户。未来若支持多用户，需要先给这两个模块加归属，不在本模块范围内。

### 页面与交互

路由 `/pet`：

```
┌──────────────────────────────────────────────┐
│  旺财  [幼犬]  [精神很好]              [改名] │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │   夜晚/白天背景 · 窝 · 食盆 · 球        │  │
│  │                                      ● │  │
│  │            (像素狗)              ●      │  │
│  └────────────────────────────────────────┘  │
│                                              │
│  饱腹  ███████░░░  72   [喂食] [零食 ×2]     │
│  清洁  █████░░░░░  51   [洗澡]               │
│  心情  ████████░░  83   [玩耍] [遛狗]        │
│  精力  ██████░░░░  64   [睡觉] [看医生]      │
│                                              │
│  第 3 天 · 下次成长还差 4 天                  │
└──────────────────────────────────────────────┘
```

- 领养态：没有宠物时显示一张领养卡，狗预览、名字输入（默认旺财）、按钮「领养」。
- 点击狗 = 抚摸，飘一个爱心；键盘 Enter/Space 同样触发。
- 动作按钮显示冷却倒计时；不可用时按钮禁用并用 tooltip 说明原因。
- 每次操作后 1.5–2 秒播放对应动画，然后回到 idle。
- 房间背景按本地时间在 07:00–19:00 用暖色、其余用冷色；不做完整昼夜系统。
- 便便按 `poop_count` 在固定三个位置显示，洗澡后消失。
- 移动端单列，操作按钮两列换行；精灵图按容器宽度缩放，保持 `image-rendering: pixelated`。

### 像素素材规范

- 逻辑帧 64×64，透明 PNG，横向 4 列。
- v1 只有一套狗（三个成长阶段共用），阶段差异用缩放和滤镜表达；三套独立素材不作为 v1 交付。

### 默认形象

用户提供了一张三视图参考：奶油金色幼犬、垂耳、深棕描边、红色项圈，正面 / 侧面 / 背面各一。浅蓝色是参考图背景，不属于素材。

- 动画全部用侧视图：idle、walk、eat、sleep、sad、sick 都以侧面为准，四足动物侧面动起来最自然。
- 正视图用于领养卡、头像和点击抚摸时的正面反馈；背视图 v1 不用，留给后续「背对镜头睡觉 / 看窗外」。
- 配色从参考图取：奶油金主体、浅金高光、琥珀色阴影、深棕描边、红项圈；不另造一套色板。
- 动画时保持同一轮廓比例，项圈、耳朵和尾巴的位置不能在不同帧之间漂移。


- 动画行：idle（4 帧，6fps）、walk（4 帧，8fps）、eat（4 帧，8fps）、sleep（2 帧，2fps）、sad（2 帧，3fps）、sick（2 帧，3fps）。
- 用 CSS `background-position` + `steps()` 播放，不用 canvas；减少运行时开销。
- 素材来源优先级：
  1. 许可明确的 CC0/开源像素狗素材包（记录来源与许可）；
  2. 用图像生成做一版底稿，再手工修帧，保证同一角色一致；
  3. 最后才是代码绘制的占位狗。
- `prefers-reduced-motion` 时固定显示 idle 第一帧。

### API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/pet` | 返回 `{pet: PetPayload \| null, daily_bonus: {...} \| null}` |
| POST | `/api/v1/pet` | 领养，body `{name?}`；已存在返回 409 |
| PATCH | `/api/v1/pet` | 改名，body `{name}` |
| POST | `/api/v1/pet/actions` | body `{action}`，返回 `{pet, message, event}` |

`action` 取值：`feed | treat | wash | play | walk | sleep | wake | vet | pet`。

`PetPayload`：

```json
{
  "id": 1,
  "name": "旺财",
  "species": "dog",
  "stage": "puppy",
  "stage_label": "幼犬",
  "care_days": 3,
  "stats": { "satiety": 72, "cleanliness": 51, "mood": 83, "energy": 64, "health": 100 },
  "status": "hungry",
  "status_label": "饿坏了",
  "sleeping": false,
  "poop_count": 1,
  "treats": 2,
  "cooldowns": { "feed": 0, "treat": 0, "wash": 3600, "play": 0, "walk": 0, "vet": 0, "pet": 0 },
  "next_stage_in_days": 4,
  "version": 1,
  "updated_at": "2026-11-14T10:00:00Z"
}
```

- 冷却返回剩余秒数，前端用收到响应的时刻做本地倒计时，避免依赖服务器时钟。
- `cooldowns.pet` 取「5 秒冷却」和「距下一个整点的秒数」的较大值；达到每小时 +15 上限后按钮直接显示到整点的倒计时。
- 错误码：
  - `PET_EXISTS`（409）
  - `PET_NOT_FOUND`（404）
  - `PET_SLEEPING`（409）
  - `PET_COOLDOWN`（409，`details.remaining_seconds`）
  - `PET_TOO_FULL` / `PET_TOO_TIRED` / `PET_NOT_SICK` / `PET_NO_TREAT` / `PET_DAYTIME_ONLY` / `PET_SICK`（409）
  - `PET_PET_LIMIT`（409，`details.retry_after_seconds` 为到下一个整点的秒数）
  - `VALIDATION_ERROR`（422，沿用现有格式）
- 领养后立即返回完整 payload，前端不需要二次请求。

### 性能与无障碍

- `GET /pet` 读取 1 行；只有当天还没领奖励时才多两条 `exists` 查询。
- 补算循环最多 2160 次，单次请求无明显开销。
- 轮询只在页面可见时进行，离开页面停止。
- 状态条用 `role="progressbar"` + `aria-valuenow`；动作禁用时用 `aria-describedby` 关联原因。
- 精灵图 `aria-hidden`，页面提供文字状态；`prefers-reduced-motion` 停止帧动画。
- 颜色不是唯一信息，同时显示数值和文字标签。

## 已定的取舍（评审时可推翻）

1. 入口放在新增的「生活」分组，而不是「工具」。
2. 睡觉是手动切换，不做夜间自动睡；精力满自动醒。
3. 每日联动奖励 v1 就做，因为这是「顺带喂养」的核心；只加心情和零食，不加经验。
4. 抚摸不重置忽视计时，避免用连续点击逃避照顾。
5. 老年期不加速衰减，只换文案和外观，避免长期用户被惩罚。
6. 不做「重新领养」按钮，避免误删；需要重置时走数据库或后续单独设计。

## 成功标准

- 每天照顾 1–2 分钟，宠物能长期保持健康并成长。
- 完全不管约 3 天明显变差，约 4 天生病；再照顾可以恢复，不会死亡。
- 刷新页面、换浏览器、备份恢复后状态一致。
- 375px 宽度下可正常操作。
- 所有数值规则都有对应测试，不依赖手工试。
