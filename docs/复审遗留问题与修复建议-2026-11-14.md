# 工作台复审遗留问题与修复建议

**日期：** 2026-11-14
**审查版本：** `a19a7fffaa982ec792c902eb005fa0566058cd65`
**基线：** `2f2078b4312cf578d466f7487e1d50875dad43b8`

## 摘要

此前审查提出的 StrictMode 加载、子任务跨清单移动、登录失败记录清理、翻译历史计数、DNS 失败测试及 Agent 暂存拆分 UI 均已有对应实现。

本轮仍发现以下遗留问题：翻译请求跨 authority 重定向时会转发认证信息和请求体；白板资源回收的孤儿宽限期、并发一致性和账号隔离仍有缺口；文档本地草稿在正文清空时可能复活旧内容；离开页面提示不能区分已保存与未保存状态；Docker Compose 未传递新增清理配置。另缺少翻译请求 DNS 重绑定/固定 IP 传输的回归测试。

## 按优先级的问题与建议

### 1. [P1] 翻译上游重定向会泄露凭据和请求内容

**位置**

- `server/app/services/providers.py`：`_request`
- `server/app/services/public_http.py`：`fetch_public` 的重定向处理

**现象与影响**

翻译调用把 `Authorization`、API 凭据或请求内容传给 `fetch_public`。遇到 3xx 时，传输层会继续请求跳转目标，并沿用原始请求头、方法和 body。若跳转到另一主机，目标可能收到认证信息及待翻译文本。

已用两个本机回环 HTTP 服务复现：首个服务返回 302，第二个服务记录请求。使用占位凭据 `TEST_SECRET` 时，第二个服务收到：

```text
{"authorization": "Bearer TEST_SECRET", "body": "credential=TEST_SECRET"}
```

复现只使用本机服务和测试占位值，没有访问外网或真实凭据。

**修复建议**

1. 翻译上游请求默认禁止重定向；最简单安全的策略是在翻译调用中设 `max_redirects=0`，遇到 3xx 返回明确错误。
2. 如果产品必须支持重定向，只允许同 authority 跳转；authority 包括 scheme、host 和 port。跨 authority 时拒绝请求，不转发认证头、API Key、签名或 body。
3. 对 301/302/303/307/308 明确规定方法与 body 行为，避免 POST 被意外重放。

**回归测试**

- 302/307 跳转到不同 host、不同 port、HTTPS 降级 HTTP：断言第二个服务没有收到 Authorization、API Key 或 body。
- 同 authority 的合法跳转按产品策略验证。

### 2. [P2] 白板图片的 24 小时宽限期从上传时间计算，而非孤儿时间

**位置：** `server/app/maintenance.py` 的 `run_cleanup()`；`WhiteboardAsset.created_at`

**现象与影响**

清理逻辑用 `WhiteboardAsset.created_at` 判断是否超过 grace period。图片若已在白板中使用数天，之后刚失去最后一个引用，下一次清理可能立即删除，并未给本地草稿或冲突恢复保留完整的 24 小时。

**修复建议**

- 持久化 `orphaned_at` / `unreferenced_at`，仅在资源从“有引用”变成“无引用”时设置；重新引用时清空。
- 清理条件改为 `orphaned_at < now - grace_period`。
- 不要只依赖客户端上传时间推断资源何时成为孤儿。

**回归测试**

- 创建超过 24 小时的已引用图片，刚移除最后一个引用后运行清理：图片仍保留。
- 将 `orphaned_at` 调整到 grace period 前后，分别验证保留与删除。

### 3. [P2] 白板保存和孤立资源清理存在并发竞态

**位置：** `server/app/maintenance.py` 的引用扫描/删除；`server/app/routers/whiteboards.py` 的图片验证与保存

**现象与影响**

清理任务先扫描场景，再删资源；保存路径会验证图片并更新场景，但没有与清理共享的资源锁或删除前重检。若保存将一个候选孤儿重新加入场景，而清理已完成引用扫描，场景可能最终引用已删除的图片。

**修复建议**

- 让保存和清理使用同一套事务锁协议：保存验证并锁定资源；清理锁定候选资源后在事务中重新扫描/验证引用，再标记删除。
- 或采用规范化的白板图片引用表，以数据库外键/事务约束引用生命周期。
- 文件物理删除可采用“先标记、后 unlink”的两阶段流程，避免 DB 与文件系统状态不一致。

**回归测试**

- 用两个数据库会话确定性地交错“清理扫描”和“保存引用”，断言不能提交指向已删除资源的场景。

### 4. [P3] 白板图片清理未按账号作用域比较 fileId

**位置：** `server/app/maintenance.py` 的 `referenced_assets` 集合；`WhiteboardAsset` 以 `(user_id, id)` 作为资源标识

**现象与影响**

维护任务只把 `fileId` 放入全局集合，没有包含 `user_id`。同一图片 ID 在账号 A 被引用时，账号 B 的同 ID 孤立资源也会被当成仍有引用而长期保留，削弱回收效果。

**修复建议**

- 将引用集合改为 `(user_id, fileId)`，扫描场景时保留白板 owner ID。
- 按复合键判断并删除资源。

**回归测试**

- 两个账号上传同一 `fileId`；仅一个账号的白板引用该 ID；运行清理后保留被引用账号的资源并回收另一账号的孤儿资源。

### 5. [P2] 清空文档正文后旧本地草稿可能复活

**位置：** `web-react/src/docs/doc/DocEditor.tsx` 的草稿写入 effect、`importFile`

**现象与影响**

当 markdown 变为空时，草稿 effect 直接返回，不覆盖或删除现有 `localStorage` 草稿。导入空文档也只清 React 状态，不清除本地草稿。重新打开页面后，先前内容可能再次显示为可恢复草稿。

**修复建议**

- 区分“正文为空但仍是一个待保存文档”和“用户明确清空/新建空文档”。
- 用户明确清空或导入空文件时同步清除旧草稿；如果空文档也应可恢复，则持久化空内容及其时间戳，而不是跳过写入。
- 统一经过 `clearDraft` 的状态转换，避免只清组件 state、不清本地存储。

**回归测试**

- 写入非空草稿后清空正文并刷新，不应恢复旧文本。
- 写入非空草稿后导入空 TXT 并刷新，结果符合产品定义。
- 新建、恢复、打开项目和保存项目后分别验证草稿状态。

### 6. [P2] 文档离开页面提示将已保存内容也视为未保存

**位置：** `web-react/src/docs/doc/DocEditor.tsx` 的 `useUnloadWarning(Boolean(markdown.trim()))`；`web-react/src/docs/useUnloadWarning.ts`

**现象与影响**

警告条件只看正文是否非空。打开或保存非空项目后，关闭/刷新仍会触发离开确认，造成误报。当前 hook 也只覆盖浏览器 `beforeunload`，不拦截站内路由切换。

**修复建议**

- 跟踪已保存基线与当前编辑内容的差异，只有真正 dirty 时才启用浏览器提示。
- 保存成功、打开项目或显式丢弃后更新基线。
- 若要求防止站内切换丢失内容，再增加路由级离开确认；和浏览器关闭提示共用同一 dirty 状态。

**回归测试**

- 已保存项目关闭/刷新不提示；编辑后未保存应提示；取消离开后内容保留。
- 站内切换、打开另一个项目时验证同一 dirty 策略。

### 7. [P2] 保存项目的大小限制缺少足够明确的界面预告

**位置：** `web-react/src/docs/ProjectActions.tsx`；`web-react/src/docs/doc/DocEditor.tsx`

**现象与影响**

文档记录了项目 state 5 MB、单附件 20 MB 限制，但保存入口没有明确显示限制和当前内容是否接近/超过上限；用户可能到提交时才遇到失败。

**修复建议**

- 保存前计算 state 大小和待上传附件大小；超过限制时在保存入口附近显示可操作提示。
- 对本地可继续编辑/导出但不可保存的 PDF，提示具体超限附件和替代操作。
- 服务端仍保留最终校验，前端提示不能替代服务端限制。

**回归测试**

- 5 MB state 上限、20 MB 附件上限的边界值和超限值均显示明确提示；保存失败时编辑内容仍保留。

### 8. [P2] Docker Compose 未传递新增清理配置

**位置：** `.env.example`、`server/app/config.py`、`docker-compose.yml` 的 API 环境变量

**现象与影响**

新增的 `WB_LOGIN_ATTEMPT_RETENTION_DAYS` 和 `WB_WHITEBOARD_ASSET_GRACE_HOURS` 写入根 `.env.example`，但 Compose 的 API `environment` 没有转发它们。Compose 用户在 `.env` 中调整值不会影响容器，容器始终使用默认值。

**修复建议**

在 `docker-compose.yml` 的 `api.environment` 添加：

```yaml
WB_LOGIN_ATTEMPT_RETENTION_DAYS: ${WB_LOGIN_ATTEMPT_RETENTION_DAYS:-7}
WB_WHITEBOARD_ASSET_GRACE_HOURS: ${WB_WHITEBOARD_ASSET_GRACE_HOURS:-24}
```

并用 `docker compose config` 验证默认值和覆盖值都进入 API 容器配置。

### 9. [P2，测试缺口] 补充 DNS 固定 IP 的重绑定回归

**位置：** `server/tests/test_translate.py`；`server/app/services/public_http.py`

**现状：** 已新增 DNS 失败 mock，但未验证校验后的 IP 被用于实际连接。

**修复建议与测试**

- mock 解析器返回一个公网 IP，检查 HTTP 连接使用该 IP、TLS/Host 仍使用原 hostname。
- 验证连接阶段不再次按 hostname 解析。
- 验证后续重定向会独立重新校验目标，私网/回环目标被拒绝。
