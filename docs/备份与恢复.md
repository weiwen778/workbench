# 备份与恢复

设置 → 系统与备份可以提交完整备份、下载加密备份和单独下载恢复密钥。顶部任务中心显示进度、校验失败和重试入口。

默认每 24 小时备份一次，保留最近 7 份。备份包含 PostgreSQL/SQLite 数据库、附件存储及 WB_ENCRYPTION_KEY，以 AES-256-GCM 加密；恢复密钥单独保存于备份目录 recovery.key。新备份验证全部文件 SHA-256 和数据库格式成功后，才清理超过保留数量的旧备份。失败记录保留在任务中心。

请将备份与恢复密钥分别复制到其他安全位置。本机备份不能应对整块磁盘损坏。恢复密钥丢失后无法解密备份。

配置项：WB_BACKUP_ENABLED=true、WB_BACKUP_INTERVAL_HOURS=24、WB_BACKUP_KEEP=7、WB_BACKUP_DIR。WSL 默认目录为项目 .backups，Docker 为独立 wb_backups 卷挂载的 /data/backups；目录和密钥限制本机权限。备份目录必须位于附件目录之外。

## 恢复步骤

1. 停止目标工作台服务，保留当前数据，另建空 PostgreSQL 数据库和空附件目录。
2. 提供下载的 .wbbackup 和 recovery.key。PostgreSQL 恢复工具版本不能低于创建备份的 pg_dump 版本。
3. 在环境变量 WB_RESTORE_DATABASE_URL 指定空目标数据库连接，运行：

```sh
server/.venv/bin/python scripts/restore_backup.py /安全路径/backup.wbbackup \
  --key-file /另一安全路径/workbench-recovery.key \
  --storage-dir /恢复目标/storage \
  --recovery-env /恢复目标/recovered.env
```

Docker 镜像内也可执行 `python -m app.restore_backup`，参数相同。以一次性容器运行，挂载备份、密钥和空目标目录；不要同时启动工作台访问该目标数据库。

4. 恢复工具先验证完整加密流与全部文件哈希，拒绝覆盖非空数据库、非空附件目录或已有 recovered.env。
5. 将 recovered.env 中的 WB_ENCRYPTION_KEY 应用到目标服务配置，同时配置目标数据库和附件目录。不要将 recovered.env 放进 Git。
6. 在目标环境执行 `alembic upgrade head`，再启动服务，登录后检查表格、笔记、附件和翻译配置。

恢复后旧登录会话和 Agent 令牌全部撤销，需要重新登录/创建令牌；排队或执行中的后台任务标记为中断，避免旧任务自动重放。已有 Agent 暂存仍需人工审核。恢复到空目标不等于切换生产环境，核对后再切换服务配置。

## 运行边界

当前后台任务按单工作进程部署；生产启动命令只启动一个 Uvicorn 进程。不要让多个同数据库服务同时启动任务工作器。服务重启会将未完成任务标记失败，由用户核对后重试。

备份在服务运行时取得数据库快照并收集附件。附件应通过工作台操作；文件被并发删除或替换时，完整性校验可能失败，请在任务中心重试。正常读取和编辑不会因备份被整体暂停。
