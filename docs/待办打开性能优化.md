# 待办打开性能优化（2026-11-04）

## 原因与改动

原来每个待办行都渲染一套隐藏编辑弹层，里面有日期、时间、文本等控件。首屏 50 条未完成任务时，实际创建约 154 个弹层、近 300 个输入控件。接口耗时仅 14–16 ms，主要阻塞来自前端控件初始化。

- 编辑改为一个按需创建的共享弹窗，只有点击编辑才挂载表单。
- 快速添加的截止时间面板关闭时不渲染内容。
- 已完成区域默认折叠，展开时再挂载。搜索定位到已完成任务时自动展开，保留完成任务和子任务的操作能力。
- 保持未完成首屏 50 个父任务和原有子任务展示。按截止日期模式不挂载不可用的上下移动按钮，手动排序模式显示。
- 首批数据准备好后再挂载任务 TransitionGroup，避免初次进入给全部任务播放插入动画；完成和重排操作仍保留反馈。
- 列表数据使用 shallowRef，避免只读行对象的深层响应代理。
- 进入已选择清单时直接获取 /todos；接口已返回清单元数据，不再先请求 /todo-lists。将响应中的清单信息交给侧栏，避免读完任务又发一次清单请求。
- 用请求序号和页面有效标记隔离迟到响应，切换清单后旧数据不会回写列表或侧栏。

## 测量

WSL 本地 PostgreSQL、生产构建、Chromium 1440×1000，导航至首屏待办显示且加载遮罩消失。两张现有模拟清单的单轮测量，不代表所有设备或云端延迟。

| 清单 ID | 首屏耗时 | 最长主线程阻塞 | 输入控件数 | 隐藏弹层数 |
| --- | --- | --- | --- | --- |
| 1 | 975 → 355 ms | 711 → 84 ms | 286 → 74 | 154 → 1 |
| 2 | 893 → 307 ms | 639 → 68 ms | 287 → 74 | 154 → 1 |

优化前后均显示 50 条未完成父任务。已完成区域改为默认折叠，已完成子任务的 DOM 因此延后创建。清单元数据请求由首次进入时 3 次降到侧栏需要的 1 次；清单内刷新直接复用 /todos 返回的元数据。

## 验证

- npm run build：类型检查、生产构建和预压缩通过。
- 后端原有待办测试 13 项通过。
- e2e/todos-open-performance.mjs，在临时独立服务器 18188 验证：首次精简渲染与请求数、编辑保存和清空截止日期、完成与撤销、子任务驱动父任务状态、手动排序、分页、定位已完成任务、切换清单时迟到响应保护、移动端。
- 性能测量只读现有模拟清单；增删改测试使用隔离数据库，不写入本地业务待办。
